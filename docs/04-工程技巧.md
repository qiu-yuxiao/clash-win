# 04 工程技巧

> **端口口径变更（2026-11-09 补注）**：文中的单实例探测 `33337`、内核 `10811`、控制器 `9108` 属 v0.2.1 之前的端口错开方案；当前为 `33335` / `10801` / `9098`（`include/clashwin/config/constants.h:22-31`）。技巧本身仍适用，替换端口即可。

本项目的验证环境有两条硬约束：360 主动防御会拦截 `build\bin\Release` 下进程的写操作；本工具链的后台 shell 命令仍受沙箱写限制。下面每条都是为此磨出来的可用做法。

## 1. 测试 exe 隔离运行（首选）

`scripts/run_tests_v4.ps1` 把 `clashwin_test.exe` 复制为 `%TEMP%\cwrun\cwrun.exe`，同时复制 `locales` 与 `assets\locales`，并把 `TMP/TEMP` 重定向到 `%TEMP%\cwrun\tmp` 后清空再跑。

对照数据：在 `build\bin\Release` 原地直跑，出现过写盘 `err=5`、进程卡死并锁住 exe（后续 MSBuild 报 `LNK1104`）、甚至 `0xC0000005`；同二进制在 `cwrun` 下 531 cases 全量通过。结论：**测试永远走隔离目录**，原地跑只用于怀疑环境问题时做对照。

## 2. DPI-aware 探针

PowerShell 默认非 DPI 感知，`GetDpiForSystem()` 返回 96，量出来的窗口矩形会被系统虚拟化。探针开头调用：

```powershell
Add-Type -TypeDefinition '...' # SetProcessDpiAwarenessContext(-4) + GetWindowRect
```

再读 `GetWindowRect` 才是真实物理矩形（本项目 150% 缩放下为 406×1021，逻辑 271×681）。量 UI 前先打印 `GetDpiForWindow`，不要假设 96。

## 3. PrintWindow 抓帧 + WinRT OCR

截图用 `PrintWindow(hwnd, hdc, 2)` 抓整窗（会话工作区脚本 `capture_window.ps1`，flag 2 = `PW_RENDERFULLCONTENT`），再用 WinRT `Windows.Media.Ocr` 识别（`ocr_image.ps1`）。

注意：WebView2/Tauri 窗口在 PrintWindow 下可能全黑（Mini 侧就出现过纯黑帧）；此时改用屏幕 `CopyFromScreen` 并先 `SetForegroundWindow` 摆正位置。OCR 结果只用来对照行高/文案，不用于反推尺寸。

## 4. 同屏并排对照

`pair_setup.ps1` 把 Mini 与本程序并排摆到固定坐标（各 407×1022），`pair_capture.ps1` 一次抓双窗，产出 `cmp_<页面>.png`。裁剪用 `crop.ps1`，逐区域 OCR/像素扫描。好处是同一帧、同一缩放、同一主题，差异一眼可见，且能直接量 DIP 偏移。

## 5. 崩溃钩子（抓到 0xC0000005 的真因）

Release 无 PDB 时，WER 只给 `模块+偏移`，符号化靠不住（`/OPT:ICF` 会把不同 lambda 的 `_Copy` 折叠到同一地址，本项目就因此误判到 `cmd_profile`）。有效做法是进程内 `SetUnhandledExceptionFilter`：

- 记录 `ExceptionCode`、`ExceptionAddress`、模块相对偏移、`GetCurrentThreadId()`；
- 对 `0xC0000005` 额外记录读/写类型与坏地址（`ExceptionInformation[0..1]`）；
- `CaptureStackBackTrace(2, 62, ...)` 抓栈帧并换算成 `app_off`；
- 用 `CreateFileW`+`WriteFile` 直写 `logs\crash_<pid>.log`，绕开可能已卡死的日志互斥锁。

拿到偏移后再用 `dumpbin /DISASM` + `clashwin.map` 定位函数体；若符号名可疑，读反汇编确认真实调用点。修复后必须移除钩子。

## 6. 启动进程的正确姿势

- 后台 `Start-Process` / `cmd /c start` 会让 shell 等待子进程，工具侧表现为超时；改用 WMI：

```powershell
(Invoke-CimMethod -ClassName Win32_Process -MethodName Create -Arguments @{CommandLine="$d\clashwin.exe"}).ProcessId
```

- **误判陷阱**：工具超时会连带杀掉 GUI 子进程（作业对象回收），表现为"启动 7~15 秒后进程消失、日志断在 WS 连接处、无 WER 事件"，极易被误判成崩溃。判定方法：改用 WMI 创建（脱离作业对象）后同一二进制可稳定存活；若仍崩再查代码。本轮因此白排查了一轮，记录在此避免重犯。

- 崩溃后的僵尸进程常出现 `Stop-Process`/`taskkill` 拒绝访问、线程数 0；此时改 `OutDir` 到新目录再链接，别和锁文件硬碰。
- 需要写 `build\` 或 `bin\` 的命令必须**前台 + 关闭沙箱**执行；后台命令即便声明关闭沙箱，仍会在建目录/写 tlog 处报"访问被拒绝"（本轮实测）。

验证"本程序只允许一个实例"用 connect 探测而非看进程数：

```powershell
$c = New-Object Net.Sockets.TcpClient; $c.Connect('127.0.0.1', 33337)
```

## 8. 代码签名（本机自签 + 发行边界）

### 8.1 参照对象的真实情况

Clash Mini（`ClashVerge`）**没有做 Windows Authenticode 签名**：

- `src-tauri/tauri.conf.json` 的 `bundle` 段无 `certificateThumbprint` / `signingIdentity` / `signCommand` / `digestAlgorithm`；
- `.github/workflows/release.yml` 里 "Sign setup.exe and generate .sig" 用的是 `pnpm tauri signer sign`——这是 Tauri 更新器的 minisign（Ed25519）`.sig`，只用于校验自动更新包，**不是** Windows 代码签名；
- 仓库内无 `signtool`、`WINDOWS_CERTIFICATE`、Azure Trusted Signing 之类配置。

因此 Mini 的安装包在 UAC 上同样显示"未知发布者"。不要把它当成签名范例。

### 8.2 本机开发签名（scripts\sign.ps1）

- 证书：`New-SelfSignedCertificate -Type CodeSigningCert -Subject CN=ClashWin`（RSA 4096，5 年，EKU=1.3.6.1.5.5.7.3.3）；存在且带私钥则复用，保持幂等。
- 信任：公钥证书导入 `Cert:\LocalMachine\Root` 与 `Cert:\LocalMachine\TrustedPublisher`（一次性，需管理员）。
- 签名：Windows SDK 的 `signtool sign /sm /sha1 <thumbprint> /fd sha256 /tr http://timestamp.digicert.com /td sha256`。
  - **`/sm` 必带**：证书在 `LocalMachine\My`，不带 `/sm` 会报 "No certificates were found that met all the given criteria."。
  - 证书 `/sm` 读私钥需管理员，脚本检测到非管理员会自提升（UAC 一次）。
- 接入：`installer\build_installer.ps1` 在暂存前签 Release 产物、在 NSIS 出包后签安装包；`cmake --build --target installer` 因此自动带签名。
  顺序必须是"先签 bin → 再打包 → 再签 setup"，否则安装后的 exe 仍是未签名版本。

### 8.3 卸载器签名（已解决，NSIS 两步打包）

**结论：无需换 WiX/MSI。** 成本对比：①NSIS 编译期签卸载器 blob —— 只改 `!uninstfinalize` 一行钩子 + 一个脚本；②WiX/MSI —— 重写安装包（perMachine、快捷方式、服务、卸载清理全部重做）。显然①成本更低，已落地：

- NSIS 3.11 的 `!uninstfinalize` **不注入** `UNINSTALLER_OUT_FILE`、**不追加**输出路径参数（实测：参数个数 0、环境变量为空），所以不能按官方文档想当然传路径。
- 但卸载器 blob 在编译期确实落盘为 `%TEMP%\nstXXXX.tmp`（长度与编译输出 `Uninstall code+data` 完全一致）。`!uninstfinalize` 执行时该文件已存在。
- 做法：`clashwin.nsi` 里 `!uninstfinalize` 调 `scripts\sign_nsis_uninstaller.ps1`，脚本按"最近 N 分钟内生成、≥20KB 的 `nst*.tmp`"定位 blob，用 `signtool /sm` 就地签名；NSIS 随后把**已签名**的 blob 嵌入安装包，安装出来的 `uninstall.exe` 即 `Status=Valid`。
- 约束：**makensis 必须以管理员运行**（私钥在 `LocalMachine\My`），否则钩子签名失败。`build_installer.ps1` 现已自提升一次（UAC 一次，后续 `sign.ps1` 不再弹），并在编译后校验钩子日志 `UNINST_SIGN_RC=0` + `UNINST_SIGN_VERIFY=Valid`，不满足直接失败不出包（避免"主程序已签、卸载器未签"的半成品）。
- 实测证据：合成安装包安装后 `uninstall.exe` 为 `Valid`，`SignerCertificate.Subject=CN=ClashWin`。

边界仍在：自签证书只在本机受信任。换机器/CI 构建时证书不存在，需重新生成或导入同一张证书（PFX + 密码存入 CI secret）。

### 8.4 发布前必办项

- [ ] 采购并配置公网可信代码签名证书（OV/EV，或 Azure Trusted Signing），替换本机自签证书；
- [ ] 在 CI 中通过 secret 注入证书（PFX + 密码），`sign.ps1` 改为从环境变量取证书；
- [x] 卸载器签名：用 `!uninstfinalize` 钩子签编译期 `nst*.tmp` blob（见 8.3），无需换 WiX/MSI；
- [ ] 对发布产物开启时间戳校验（`Get-AuthenticodeSignature` 必须为 `Valid` 且 `TimeStamperCertificate` 非空）；
- [ ] 如需减少 SmartScreen 冷启动警告，EV 证书或 Azure Trusted Signing 仍是唯一可靠路径（自签无法消除公网 SmartScreen 提示）。


## 2026-11-05 夜间收口技巧

- 开关逐像素：以同行左侧 8px 为背景参考，`|ΔR|+|ΔG|+|ΔB| ≥ 8` 连续 2px 定轨道边界；OFF 浅 thumb 用 `L≥210 且 B≥150`，ON 金 thumb 用 `R≥250/G≥195/B≤160`。150% 下名义 23.8×11.9 DIP = 35.7×17.85 px，实测 36×18 px 属 AA 取整。
- 行盒对齐：CSS `13px×1.57≈20.4` 的行盒在 D2D Top 对齐下等价为 y 偏移 `(20.4-18)/2 = 1.2`，比改字号更能保持字形基线；OCR 三行 y 可直接验证（745/785/820）。
- 帮助菜单取内核版本：`cmd::mihomo()->get_version(300)` 返回 `MihomoVersion{meta,version}`；`meta` 为真且串内无 `Mihomo` 时追加，取不到则不拼后缀，避免写死版本。
