# 03 踩坑与避坑清单

> **端口口径变更（2026-11-09 补注）**：v0.2.1 起端口已全量 1:1 对齐 Clash Mini（`10801/10802/10803`、guard 兜底 `7899`、controller `9098`、单实例 `33335`，见 `include/clashwin/config/constants.h:22-31`）。本文中的 `10811–10814` / `9108` / `33337` 是**当时现场的真实记录**，保留原样不作改写；复现历史场景时按当时端口理解，验证当前构建时按常量理解。

每条都是本项目真实发生过的错误，按"现象 → 根因 → 正确做法"记录。

**缺陷三类（审计时逐类扫）**
1. **做错**：搬了 Mini 的行为但实现有误（数值、时序、语义）。清单中的多数条目属于此类。
2. **自编**：Mini 没有依据，凭观感/猜测新增（如第 7 条按截图反推常量）。
3. **漏搬**：Mini 里**已有**的功能/链路，本程序没搬或只搬了一半。此类最难发现——代码能编译、单点能跑，只在"换一台干净机/换一条分支"时暴露（如第 27 条服务自举）。审计必须对照 Mini 的调用链逐跳核对，而不是只看我方代码是否"看起来有"。

**1. 界面整体放大约 1.5 倍，但窗口又只占 2/3 屏**
现象：控件看起来大一圈，窗口却比 Mini 小。
根因：物理像素与 DIP 混用——`GetDpiForWindow=144` 时，把物理矩形当成逻辑矩形交给布局，D2D 又按 144 再缩放一次。
正确做法：布局一律用 DIP；物理尺寸 = DIP × dpi/96 只在 SetWindowPos/GetWindowRect 边界换算一次。

**2. 文字二次缩放（胶囊实测 ≈19px，Mini 为 12–14px）**
现象：同一处文字比其他文本明显大。
根因：字号先按 DIP 设定，又被绘图路径按 1.5 倍再乘一次。
正确做法：`TextStyle.size` 直接作为 DIP 传给 DWrite，禁止在绘制层再乘缩放系数。核对时给出"源码字号 → 实际 DIP → physical 行高"三列数字。

**3. window_state.json 落盘出 270.667、406×860 这类怪值**
现象：重启后窗口尺寸飘，同一次读写里既有带小数的逻辑值又有物理尺寸。
根因：写入时把 DIP（含小数）与物理像素混存，读回再各按一半缩放。
正确做法：落盘统一存 **DIP 整数**（现网实证：`build/bin/Release/window_state.json` 为 `{"width":271,"height":681}`），物理换算只在 Win32 边界做一次；钳制与脱屏守卫在换算之后做。

**4. 标题栏按钮点不动，日志显示命中了 Label**
现象：点"最小化"没反应，点齿轮也无效。
根因：Label 的 `hit_self` 为真且 z 序高于按钮，点击全被文字吃掉。
正确做法：纯展示 Label 设 `hit_self=false`；命中顺序按 z 序自顶向下，先按钮后文字；改完用注入验证三段证据。

**5. 抽屉打开后标题栏被吃掉**
现象：设置抽屉铺满整窗，最小化/关闭/齿轮都点不到。
根因：抽屉挂载在窗口根 Stack，而不是内容区。Mini 的抽屉渲染在 `.layout-content` 内（`src/pages/_layout.tsx:1402-1403`；该容器自 `:1254` 起，高度 `calc(100vh - 30px)` 见 `:1260`，即标题栏占 30px），而标题栏 `customTitlebar`（定义 `:1120`、className `the_titlebar` `:1124`、渲染 `:1211/:1252`）始终在它上方。
正确做法：树改为 `Column{ TitleBar, Stack(flex 1){ MainScene, SettingsDrawer } }`，抽屉只覆盖内容区；关闭钮位置对齐 Mini（`absolute top:3 right:8`，`:1282-1287`）。

**6. 胶囊里名称与延迟间距过大，延迟被挤出**
现象：节点名占满，延迟被截断或看不见。
根因：名称用了固定宽/两端对齐，未实现"可收缩 + 省略"，把延迟推出去。
正确做法：名称 `width=min(text_w, avail)` 且可收缩省略，延迟固定宽不收缩，间距按 `active-node-card.tsx` 的 `gap:1.5`（12px）；整组居中。

**7. 按截图反推 UI，欠下 10 处无源码依据的 C 类常量**
现象：一轮"看着像"的微调后，多处数值与源码对不上，反复返工（依据：用户审计裁决）。
根因：跳过了"读源码"，用像素测量替代规范。
正确做法：一律先落"文件:行号"，`ui_src_gate.ps1` 卡住无出处常量；截图只作验证。

**8. 误删托盘"轻量模式"入口**
现象：托盘菜单比 Mini 少一项。
根因：把"看起来不常用"的菜单项当成冗余删除。该入口现已恢复，见 `src/system/tray.cpp:49`（`轻量模式 / Lite mode`）。
正确做法：菜单集合 1:1 照抄 Mini，删除任何用户可见入口前必须先对源码。

**9. 把"共用服务"误解成"禁止安装/重装"**
现象：安装器/服务逻辑被卡住，认为已有服务就不能装。
根因：把 `clash_verge_service` 的"共用"读成"独占"。
正确做法：服务名固定不变；已存在则复用，不存在则安装；卸载不清除他人依赖的服务。

**10. 端口与管道名硬编码漏改**
现象：配置写进自家目录，界面数据却来自 Mini 内核；或 mixed 端口仍是 10801。
根因：从 Mini 源码整段搬运时，只改了 `constants`，散落各处的字面量没同步。已核对的对照：Mini 管道 `\\.\pipe\mini-mihomo`（`src-tauri/src/utils/dirs.rs:184`），本程序为 `\\.\pipe\mini-mihomo-win`（`src/util/dirs.cpp:210`）；mixed 端口 Mini `10801` → 本程序 `10811`（`include/clashwin/config/constants.h:24`）。
正确做法：全部收敛到 `include/clashwin/config/constants.h`；改完 `grep` 全仓旧值，确认零命中。

**11. 默认拉起 TUN，抢占默认路由导致整机断网**
现象：`0.0.0.0/0 → 198.18.0.2`，出网 502、直连不通。
根因：启动时"恢复上次状态"或默认值把 `enable_tun_mode` 置真，未做"未显式开启不接管"的守卫。
正确做法：默认关闭；启动无条件复位为关闭；仅用户显式操作才写 TUN 配置，并校验默认路由归属。

**12. 启动即崩溃 0xC0000005（`clashwin.exe+0x109430`）——已闭环**
现象：日志止于 render target 就绪，窗口不显示，WER 报 AV。
根因：`std::make_unique<Stack>()` 后 `flow_->add_child(std::move(content))`（`src/ui/main_window.cpp:243`），随后仍用 `content->add_child(...)`（原 `:247`）——use-after-move，`this=nullptr`，`children_.push_back` 访问空对象。
正确做法：move 前取裸指针 `Stack* content_raw = content.get()`（`src/ui/main_window.cpp:241`），`scene`/`drawer` 全部经 `content_raw` 挂载（`:247`、`:252`）。
同类扫描（全仓 `std::move` 后再用同名变量，另扫 `unique_ptr` 移出后 `.get()/->` 残留）：
  - 真隐患 1 处：`src/core/core_manager.cpp:63` 原 `entries.push_back(std::move(entry)); p += entry.size() + 1;`——move 后 `size()` 未指定（实测 0），环境块步进错位。已改为先取 `const size_t entry_len = entry.size();`（`:62`），再 `p += entry_len + 1;`（`:64`）。
  - 误报 3 条（4 行，语义安全，不改）：`src/config/draft.h:52-53`（shared_ptr move 后 `reset()`，合法）；`src/config/prfitem.cpp:472` 与 `:555`（`opt = clean_download_option(std::move(opt))` 后已重新赋值）；`src/core/auto_select.cpp:59-60`（`else if (kept.empty())` 与 move 分支互斥）。
  - `add_child(std::move(...))` 全仓命中 80 处，除上述已修的 `main_window.cpp:243` 外，其余均为"先取 `x.get()` 存裸指针、再 move"，无 move 后复用。
防复发断言：`Widget::add_child` / `insert_child` 入口 `assert(w != nullptr && "...std::move 后复用")`（`src/ui/widget.cpp:37`、`:44`），头文件注明所有权约定（`src/ui/widget.h:60-63`）；`MainScene::attach_quick_bar` 删除裸指针重载，只留 `unique_ptr` 版本（`src/ui/main_scene.h:31-33`），避免静默接管所有权。
稳定性复验（2026-11-04，PID 10660）：连续运行 60.5 秒，两轮"开抽屉→日志弹窗→关抽屉→切页面→切节点→最小化/恢复→缩放窗口"，各步进程存活、线程数无骤降，全程无 `0xC0000005`、`logs/` 下无 `crash_*.log`、应用事件日志无 clashwin 报错；缩放触发 `[DPIARCH]` 两次、抽屉触发 `[GEAR]` 两条，证明 UI 事件循环未断流。修复"节点行点击"与"胶囊延迟格式化"后的最终构建（PID 14940）再跑一轮 60.4 秒：22 线程恒定、`NO_CRASH_LOG`、`Get-WinEvent` 无 Application Error。

**13. 图像内容审查挡住截图，无法目视**
现象：截图文件存在，读图被拦截，只能靠猜。
根因：图片读取走了内容审查，非本项目可控。
正确做法：不依赖目视——用 OCR 取文本、用像素直方图/行扫描取结构与色值、必要时输出裁剪小图；结论仍以源码为准。

**14. 步数/上下文上限中断，工作断在半途**
现象：连续执行到上限被截断，下一步不知道做到哪。
根因：没有中途落盘结论。
正确做法：每完成一段就写一行结果并落盘代码；恢复时先读 `docs/README.md` 的"当前状态"再继续。

**15. `profiles.yaml.current` 指向测试残留，10811 永不通**

**16. `0xC0000409`（BEX64）双击即崩 → 已符号化到具体函数/行（不是环境噪声）**
现象：2026-11-04 18:19:41 / 18:20:22 双击 `build\bin\Release\clashwin.exe`，WER 1000、Exception code `0xc0000409`、Fault offset `0x2958ad`（PID 18768/7048 均留 dump）；`clashwin_test.exe` 也出现过同码（offset `0x414dad`）。

  - 具体位置：`src/enhance/mini_agreements.cpp:245-251`（`p["name"]` / `p["server"]` 取到未定义节点）；`src/enhance/field.cpp:48-52`（原 `is_string_key` 先 `IsScalar()`，未定义即抛）；`src/core/monitor.cpp:39,51`（该 exe 构建于 15:17:51，守护线程的 `tick_once()` 当时没有 try/catch，异常逃逸线程边界 → terminate → abort；兜底 catch 是 15:51 才加的，晚于该二进制）。
修复：`field::is_string_key` 先 `IsDefined()` 再 `IsScalar()`（[field.cpp:51](file:///C:/Users/sun_y/Documents/AntiGravity_Projects/ClashWin/src/enhance/field.cpp#L48-L52)）；`CoreMonitor::start()` 的 `std::thread` 内 `try { tick_once(); } catch (...)` 兜住（[monitor.cpp:51-57](file:///C:/Users/sun_y/Documents/AntiGravity_Projects/ClashWin/src/core/monitor.cpp#L39-L57)）。
复核（2026-11-04 21:10/21:13，`scripts\run_app_test.ps1` 四项目检全过）：旧二进制在仓库路径 5/5 PASS、`%TEMP%\cwrun\app` 复制路径 5/5 PASS，均 0 次 WER 1000 —— 崩溃由当时的配置内容触发（代理项缺 `name`/`server`），不是路径或工具作业对象导致；该配置已于 20:53 被覆盖，故用现配置无法复现。测试固定「复制到 `%TEMP%` 隔离目录 + 以 repo 为 cwd」仍是隔离纪律（cwd 供 `assets/locales` 等相对路径回退，见 `tests/test_t25_p1_finalization.cpp:608-614`），但不再是规避崩溃的手段。

**17. 僵尸测试进程占 exe 镜像锁 → `LNK1104`**
现象：改完断言重编报「无法打开 clashwin_test.exe」。
根因：十余个历史 `clashwin_test` 进程（12:47–17:45）仍持有映像。
正确做法：先 `Get-Process clashwin_test | Stop-Process -Force`，再用 `[IO.File]::Open($exe,'Open','ReadWrite','None')` 探测锁已释放，再重编。不要盲删 bin 目录。

**18. 360 拦截工具拉起的 GUI：不写日志、不建子进程**
现象：WMI/Explorer 启动 `clashwin.exe` 能出窗口（`MainWindowTitle=Clash Win`、`33337` LISTENING），但 `logs\clashwin.log` 不新增、`sidecar` 不启动、10811 不监听；同一二进制在 14:xx 由用户上下文启动时日志正常。
根因：安全软件对「未知签名 exe + 工具作业对象」的文件写/`CreateProcess` 拦截，失败被 `Logger::init` 的静默降级吞掉（`src/util/log.cpp:23-27`）。
正确做法：运行期证据拆成两路——①内核直拉（`verify_10811.ps1`，与 App 同参数 `-d <home> -f clash-win.yaml -ext-ctl-pipe \\.\pipe\mini-mihomo-win`）+ 命名管道 HTTP 取 `/configs`、`/proxies`、`/connections`；②UI 侧证据用 `/connections` 的 `active/downloadTotal/uploadTotal`（即 UI WS 数据源）与截图。启动被测程序是测试方的活：固定用 `scripts\run_app_test.ps1`（WMI 脱离作业对象 + 四项自检 + 截图 + Post 清理），不要求用户手动双击。

**19. 实验环境未清理 → 多实例/端口占用/僵尸占锁，结论全被污染**
现象：同一时段出现两个 `clashwin.exe`（18:19:41、18:20:22）且 33337 无监听；随后多次撞上「端口被占」「僵尸进程占 exe 镜像（LNK1104）」「旧实例抢单实例端口」，每次都要事后排查才知道环境不干净。
根因：实验前没有固定基线，谁先起、谁没退、端口归谁全靠现场猜；工具拉起的进程退出后 PID 条目还会被启动器句柄保留（0 线程/0 句柄），看着像"两个实例同时活着"，实际是已退出的僵尸条目。
正确做法（已制度化）：
  - 任何「启动程序做实测」前后各跑一次 `scripts\env_guard.ps1 -Phase Pre / -Phase Post`。
  - **Clash Win 的全部实例都是测试启动的，不存在"用户在用的实例"**：Pre 与 Post 一律清空 `clashwin.exe`、`clashwin_test.exe` 全部实例，以及仓库 `build*` / `%TEMP%\cw*` 目录下的 `mini-mihomo.exe`，不设任何豁免开关（无 `-Force` / `-KeepExisting`）。
  - 清理可审计：每条输出 `PID | 进程名 | 完整路径 | 启动时间 | SUCCESS/FAILED/SKIP`；360 拒绝时打印错误消息 + 提权命令。
  - 断言：自家存活进程数 = 0；`33337`、`10811–10814`、`9108` 全部空闲（Clash Mini 占 10801/53 属正常，不判失败）→ `READY / clean`；否则 `NOT READY / NOT CLEAN` 并退出非 0。
  - 僵尸 PID 条目（0 线程/0 句柄，进程已退出、句柄被启动器持有）无法 Kill，单列 WARN 并计数，不计入"存活进程数"。
  - 唯一排除：`clash-mini.exe`（含 `Program Files\Clash Mini` 下内核）与 `clash_verge_service`/`clash-verge-service`，永不清理。
  - 实验报告必须带 Pre 基线行与 Post 结论行，否则视为未验证。


**20. 测试为验证出网去开 TUN / 系统代理 → 默认路由被劫持、用户断网，且测试完不还原**
现象：实机检查出现 Mihomo Meta Tunnel Up、0.0.0.0/0 → 198.18.0.2 抢占默认路由；另有 ProxyEnable/ProxyServer/AutoConfigURL 被写过但没还原的痕迹。用户网络设置被测试改动，下一次实验的结论全部不可信。
根因：把「验证 Clash Win 能出网」误解成「必须先把整机流量切到 Clash Win」。实际上内核有 mixed-port，验证只需显式代理；TUN/系统代理属于「设置网络」，不是「使用网络」。
正确做法（已制度化）：
  - 验证出网只用显式代理：curl -x 127.0.0.1:10811 https://www.gstatic.com/generate_204、Invoke-WebRequest -Proxy http://127.0.0.1:10811，或直接查内核 GET /proxies、GET /connections 的 active/downloadTotal/uploadTotal。禁止为此开系统代理或开 TUN。

**21. 单实例监听 socket 被 sidecar 继承 → App 退出后 33337 仍 LISTEN**

根因：`socket()` 创建的句柄默认带 `OBJ_INHERIT`；拉起 sidecar 的 `CreateProcessW` 必须 `bInheritHandles=TRUE`（`STARTF_USESTDHANDLES` 重定向 stdout/stderr，[core_manager.cpp:449](file:///C:/Users/sun_y/Documents/AntiGravity_Projects/ClashWin/src/core/core_manager.cpp#L449)），监听 socket 遂被 `mini-mihomo.exe` 继承，本进程退出后内核仍持有该端口。
修复：在源头清继承位，覆盖所有 spawn 调用点——[singleton.cpp](file:///C:/Users/sun_y/Documents/AntiGravity_Projects/ClashWin/src/app/singleton.cpp) 创建监听 socket 后与 `accept()` 返回的连接 socket 各加 `SetHandleInformation(h, HANDLE_FLAG_INHERIT, 0)`。

**25. 交付二进制与验证二进制不一致 → 用户复现出「按钮动了但功能没动」**
现象：用户点 TUN，UI 三段切到 TUN、`enable_tun_mode=true` 已写入，但服务/内核没换；用户以为产品缺陷。
根因：给用户操作的窗口来自 `C:\Program Files\ClashWin\clashwin.exe`（03:41 构建），不含服务模式接线；我们验证的是 `build\bin\Release\clashwin.exe`（14:18 构建，含 `core start decision`/`needs_tun`/`service_mode`）。同名进程两个来源，用户点开的不是最新那个。
正确做法（已成硬规则）：
- 交付**单一事实源**：唯一登记路径 `build\bin\Release\clashwin.exe`；交付说明必须写 `path + SHA256 + mtime`；其它目录的同名进程一律先杀。
- 交付前跑 `scripts\delivery_check.ps1`（先 `-Record` 记录基线，交付前不带参数校验）：SHA256 与刚构建产物一致、二进制含接线标记串（`core start decision`/`needs_tun`/`service_mode`/`clash_verge_service`/`/proxies/`/`Service started core successfully`，ASCII 与 UTF-16LE 两种编码都查）、`clashwin` 唯一且路径=登记路径、`clash_verge_service` RUNNING 且 ImagePath 指 Mini、`ProxyEnable=1`/`ProxyServer=127.0.0.1:10811`/TUN OFF。全部 PASS 才交付。
- 判定口径：`clashwin` 进程数 ≠ 1 或路径 ≠ 登记路径 → 直接判交付失败，不再往下测。

**26. 杀内核但没关系统代理 → 整机断网**
现象：杀掉 sidecar `mini-mihomo` 后浏览器全部打不开，用户报「整机断网」。
根因：`ProxyEnable=1` 仍指向 `127.0.0.1:10811`，此时 10811 无人监听；所有走 WinINET 的程序（Edge/curl/IWR）全部超时。链路与 DNS 正常，卡在「代理层」。
正确做法：停内核顺序固定为「先 `ProxyEnable=0`（或还原基线）→ 再停 TUN/删路由 → 最后杀进程」；回滚脚本把注册表还原放在第一步。排查口径：`ping` 网关与 `Resolve-DnsName` 都通、HTTP 全超时 → 九成是代理指向死端口。

**27.【漏搬】服务自举与独立可用性（Mini 有，本程序没搬全）**
现象：在"Mini 已装服务"的机器上切 TUN 能通，于是被判为可用；换到干净机（无 `clash_verge_service`）后 TUN 起不来，或只发了 IPC 请求就报成功。
根因：Mini 在切 TUN 前有完整的"可用性门控 → 安装 → 重启内核"链路，本程序只搬了"起内核"这一段：
  - Mini 前端：`src/pages/_layout.tsx:1085-1095`（`!isTunModeAvailable` → `installServiceAndRestartCore()`）；`src/hooks/use-service-installer.ts:28-43`（`installService()` → `restartCore()`）；`src/hooks/use-system-state.ts:50-65`（`isTunModeAvailable = isAdminMode || isServiceOk`）。
  - Mini 后端：`src-tauri/src/cmd/service.rs:18/28/32/38`；`src-tauri/src/core/service.rs:76-121`（非管理员走 `RunasCommand` 提权）、`:193-215`（重装/修复）、`:333-...`（就绪判定）、`:429-495`（`StartRequired`/`ReinstallRequired`/`ForceReinstallRequired`/`Unavailable` 分支）；`src-tauri/src/core/manager/lifecycle.rs:151-176`（`prepare_startup_mode`）、`:183-235`（`wait_for_service_ready` 含 installer UAC）。
  - 我方缺口：`service_ready` 只查"管道存在 + magic 握手"（`src/core/service_mode.cpp:122-126`、`src/system/service_runner.cpp:94-107`），**不查 SCM STATE、不查 `ImagePath` 是否失效**；已注册但二进制被删（Mini 卸载残壳）时会一直判定"可用"然后起内核失败。
正确做法：
  - 状态判定四态化：未安装（`OpenService` 失败）/ STOPPED（`QueryServiceStatus != RUNNING`）/ RUNNING / 就绪（IPC 可握手）。参考 `src/core/service_mode.cpp:68-126`。
  - 启动前校验 `ImagePath` 指向的二进制存在：`src/core/service_mode.cpp::is_service_binary_valid()`（`QueryServiceConfigW` → `GetFileAttributesW`）。
  - 缺失或 `ImagePath` 失效 → `run_installer(true)`（`runas` UAC，`src/system/service_runner.cpp:29-77`）→ 复核注册 → `start_service` → `wait_for_ready`；失败在 `src/core/core_manager.cpp::start_service_locked` 内 `notify("service_install_error"/"service_start_error")` 并返回错误码，不静默。
  - 安装器安装时即装服务（Mini 的 NSIS 只"存在则启动"、安装由应用内 `install_service` 完成；我方 `installer/clashwin.nsi:405-431` 已覆盖"不存在则装、存在则复用并启动"）。
  - 验收口径：见 `clash_mini_agreements.md` §1.8 五步用例；只在 Mini 已装服务的机器上通过，不算验收。
